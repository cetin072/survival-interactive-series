# STRONGHOLD — Persistent State Protocol

Status: **AUTHORITATIVE STATE RULES**

목표: 긴 연대기를 여러 채팅방에 걸쳐 이어도 세계 사실과 현재 장면을 잃지 않되, GM이 매 턴 전체 문서를 다시 읽지 않게 한다.

새 채팅방 진입 순서는 `START_ROOM.md`가 정의한다. 이 파일은 상태 계층과 충돌 해결만 정의한다.

## 1. 상태 계층

### Long State — 장기 체크포인트
- `CURRENT_STATE.json`
- `LEDGER.md` / 최신 `LEDGER_APPEND_*`
- `CANON.md`
- Character Bible
- `PLAYER_FEEDBACK.md`

Long State는 새 방 부팅, 큰 시간점프, 큰 상태변화 때 중심으로 사용한다.

### Hot State — 현재 장면
- `LIVE_SCENE_STATE.md`

`Status: ACTIVE`이면 현재 장면 연속성의 최우선 상태다.

Hot State는 짧게 유지하며 다음만 추적한다.
1. 현재 시각/장소
2. 물리적으로 함께 있는 사람
3. 원격 연락자
4. 이동/합류/통화/도착 등 pending
5. 방금 확정된 플레이어 행동과 순서
6. confirmed vs rumor/unconfirmed
7. 필요한 경우 rollback boundary

## 2. 충돌 우선순위

1. 사용자의 최신 명시 교정
2. ACTIVE `LIVE_SCENE_STATE.md`
3. `CURRENT_STATE.json`
4. 최신 LEDGER / Character Bible 보강
5. `BOOT.md` 불변 규칙
6. 오래된 `CANON.md`, Archive
7. 비활성/과거 계획 자료

`CURRENT_STATE`와 ACTIVE LIVE가 다른 날짜를 갖는 것은 정상일 수 있다.
- CURRENT_STATE = 마지막 Long State 체크포인트
- LIVE = 그 이후 진행 중인 Hot State

ACTIVE LIVE를 무시하고 CURRENT_STATE 날짜로 되돌리지 않는다.

## 3. Pending / completed 하드 규칙

예정과 완료를 같은 것으로 취급하지 않는다.
- 만나기로 함 ≠ 이미 만남
- 이동 중 ≠ 도착
- 전화하기로 함 ≠ 통화 완료
- 요청함 ≠ 상대가 수락/실행함
- 준비함 ≠ 대피/이동 완료

연속성 오류가 발생하면 억지로 이어 붙이지 않는다.
사용자 교정을 최우선으로 반영하고, 오류 이후 장면이 잘못된 전제를 사용했다면 **가장 작은 안전 지점까지 롤백**한다.

## 4. CURRENT_STATE — 장기 진실

추적 대상:
- 체크포인트 날짜/위치
- 플레이어 상태
- 핵심 자원 밴드
- 거점/차량/소유권/사용권
- 중요 인물과 관계
- 직업/사업의 현재 구조
- 지역/기관 상태
- 해결/미해결 주요 스레드
- 최근 중요한 영구 변화

CURRENT_STATE는 매 턴 실시간 DB가 아니다.

### 4-A. 중요한 비도현 관계
기존 `relationships`가 도현 중심 관계를 표현하더라도, 장기적으로 중요한 비도현 관계는 별도 edge 형태로 소수 추적할 수 있다.

권장 예시:
```json
{"between": ["최영수", "정우진"], "state": "서로 직접 연락 가능한 실무 협력", "importance": "active"}
```

원칙:
- 전체 인물쌍을 관계 그래프로 만들지 않는다.
- 실제 플레이에 영향을 줄 **최대 3~5개 정도의 활성 비도현 관계**만 유지한다.
- 협력뿐 아니라 불편함·거리·이해충돌·빚·가족문제도 기록 가능하다.
- 도현이 관여하지 않은 상태에서 실제로 변한 관계도 영구 변화면 LEDGER에 남긴다.

### 4-B. 정산되지 않은 인간 상태
숫자 호감도를 만들지 않는다.
대신 다음처럼 이후 행동을 바꿀 수 있는 미해결 인간 상태가 실제 사건에서 발생하면 짧게 추적할 수 있다.
- 갚지 못한 은혜
- 미해결 서운함
- 부담감/미안함
- 후회
- 불편한 약속
- 관계의 거리 증가/감소

돈·장비·운송비 정산과 인간 감정의 정산은 같은 것이 아니다.
사건이 끝났다고 감정까지 자동으로 0으로 만들지 않는다.

### 4-C. 발견된 욕망
GM이 욕망을 창작해 넣지 않는다.
플레이에서 반복적으로 확인된 행동이 있을 때만 `current_desires` 또는 동등한 짧은 필드로 보존할 수 있다.

예:
```json
{"desire": "회사 급여 하나에만 의존하지 않는 생활 선택권", "evidence": "반복된 독립 생계축 선택", "confidence": "confirmed_by_play"}
```

- 한 번의 선택만으로 성격을 고정하지 않는다.
- 사용자 최신 선택이 과거 욕망과 충돌하면 변화할 수 있다.
- 욕망은 `core_principles`와 별개다. 원칙은 판단 방식, 욕망은 원하는 방향이다.

### 4-D. 자원·정보·공간 상태는 실제로 변한다
- 자원 밴드는 세계 사건과 소모에 따라 상승/하락할 수 있다.
- 임의로 긴장을 만들기 위해 낮추지 않는다.
- 밴드만으로 결정이 어려운 순간에만 필요한 수량을 임시로 기록한다.
- 정보 접근성도 `높음` 고정값이 아니다. 통신·시간·신뢰도·출처 접근에 따라 변할 수 있다.
- 중요한 이동 제약은 거리, 도로 상태, 접근성, 소요시간 중 필요한 요소를 기록해 `A를 선택하면 B를 놓친다`가 실제로 유지되게 한다.

## 5. 시간과 나이

현재 캐릭터 연령 기준점은 **2032년 3월 말 활성 시점**으로 둔다.

핵심 현재 연령:
- 박도현 39세
- 한지연 38세
- 최영수 38세
- 정우진 37세

같은 세대 주변 인물도 이 기준에 맞춰 조정한다.

장기적으로 `age`는 영구 고정값으로 두지 않는다.
- 정확한 생년월일이 Canon이면 `birth_date` 사용.
- 정확한 생년은 없고 특정 시점 나이만 확정됐으면 `age_reference: {age, date}` 사용.
- `30대 후반`, `고령`처럼 인상만 확정됐으면 `age_note`를 유지한다.
- 현재 나이는 현재 게임 날짜와 age reference에서 계산/추정한다.
- 생일이 확정되지 않은 경우 한 살 단위로 억지 단정하지 않아도 된다.
- Character Bible의 과거 숫자 나이는 별도 표기가 없으면 첫 등장/기준 시점 앵커로 해석하며 현재 나이로 고정하지 않는다.

시간이 흐르면 직업, 은퇴, 체력, 외형, 부모 노화, 자녀 성장 등 서사적으로 의미 있는 변화가 생길 수 있다.

## 6. LEDGER — 영구 사건 장부

모든 턴을 기록하지 않는다. 되돌리기 어려운 변화만 기록한다.

예:
- 중요한 관계 형성/파탄
- 중요한 비도현 인물 간 관계 변화
- 사망/이탈/배신/합류
- 거점 취득/상실/대파
- 차량 취득/상실
- 큰 금전 변화
- 장기 부상
- 지역 영구 통제/붕괴
- 중요한 약속/빚/비밀/장기 원칙
- 반복 선택으로 확인된 장기 욕망의 변화

## 7. CANON / Character Bible

- `CANON.md`: 오래됐지만 안정적인 공개 사실.
- Character Bible: 반복 인물의 외형/말투/성향/독립 목표/관계 앵커.
- CURRENT_STATE와 충돌하면 최신 상태가 우선한다.
- 캐릭터 설정집의 `기본 나이`는 현재 나이 고정값이 아니라 해당 기준시점 앵커로 관리한다.
- Character Bible의 맹점은 장식 설정이 아니다. 실제 사건이 맞물리면 인물은 비합리적·불편한 선택을 할 수 있다. 다만 갈등을 만들기 위해 억지로 맹점을 발동시키지 않는다.

## 8. RAW Transcript — Cold Archive

RAW는 정상 부팅 Source of Truth가 아니다. 그러나 장기 IP 보존에서는 **가장 원본에 가까운 1차 기록**이다.

### 8-A. RAW의 기본 정의
`아카이빙`이라고 하면 기본값은 요약이 아니라 **사용자에게 실제로 보였던 플레이/피드백 대화 전체 원문 보존**이다.

원칙적으로 포함:
- 실제 USER 입력 전체: 숫자 선택, `ㄱ`, AUTO, 자유행동, 장문 전략, 정정, 불만, 피드백
- 실제 GM/ASSISTANT 공개 출력 전체: 시간·장소 헤더, 서술, 대사, 메시지, 선택지, 후일담, 메타 응답
- GM의 공개 실수와 사용자의 교정도 삭제하지 않고 원문 그대로 보존
- 시즌 종료 직후의 사용자 회고와 GM 공개 피드백도 해당 시즌 post-arc RAW에 포함 가능

RAW는 `대사만` 보존하는 것이 아니다. **사용자와 GM 사이에 실제 표시된 게임 관련 텍스트 전체**를 순서대로 저장한다.

보존 금지:
- 시스템/개발자 지침
- 비공개 내부추론 / chain-of-thought
- Hidden planning 내부내용
- Tool 내부 로그
- API key/password/token
- 게임과 무관한 실제 개인정보·민감정보

필요한 개인정보 보호는 `[REDACTED]`로 처리한다.

### 8-B. RAW와 요약본은 별개 자산
RAW와 운영용 요약은 서로 대체하지 않는다.

권장 계층:
1. `raw_transcript/RAW_*_PART_XX.md` — 실제 공개 원문 1차 자료
2. `ROOM_ARCHIVE_*` — 사건·선택·결과를 읽기 쉽게 압축한 운영 요약
3. `LEDGER*` — 되돌리기 어려운 영구 변화만
4. `CURRENT_STATE.json` — 다음 시즌 부팅용 현재 상태
5. `FEEDBACK_*` / `PLAYER_FEEDBACK.md` — 재미·GM 운영 교정

따라서 RAW가 COMPLETE여도 요약 Archive를 만들고, Archive가 완성돼도 RAW 완료로 간주하지 않는다.

### 8-C. 원문 정확성
- 실제로 문자 그대로 확인 가능한 대화만 RAW로 저장한다.
- 요약본, 기억, Canon, ROOM_ARCHIVE를 이용해 빠진 대사를 재창작하지 않는다.
- 정확한 원문에 접근할 수 없는 위치에는 `[원문 확인 불가 구간]`을 명시한다.
- 원문 오탈자, 짧은 입력, 당시 GM의 실수도 역사자료이므로 임의로 매끈하게 고치지 않는다.

### 8-D. Rolling RAW — 시즌 종료까지 기다리지 않는다
긴 채팅은 종료 전에 과거 턴이 압축되거나 원문 접근성이 떨어질 수 있으므로, **시즌 종료 때 한 번에 저장하는 방식을 금지한다.**

신규 시즌에서는 플레이를 방해하지 않는 범위에서 Rolling RAW를 자동 수행한다.

기본 규칙:
- 약 6~10개의 USER↔GM 왕복, 또는 큰 장면 하나가 끝날 때마다 아직 저장하지 않은 공개 원문을 `RAW_*_PART_XX.md`에 순서대로 flush한다.
- 큰 시간점프, 중요 관계 전환, 큰 자산 변화, 방 이동 직전에는 즉시 flush한다.
- 사용자가 별도로 `저장해`라고 말하지 않아도 수행한다.
- 이미 저장된 턴을 중복 기록하지 않도록 마지막 저장 경계를 유지한다.
- 원문 저장 때문에 플레이 본문에 메타 알림을 매번 띄우지 않는다. 실패나 누락 위험이 있을 때만 알린다.

### 8-E. 시즌 종료 RAW Final Flush
시즌 종료가 결정되면 새 시즌 장면을 시작하기 전에:
1. 아직 저장되지 않은 USER/GM 공개 원문을 마지막 PART에 저장한다.
2. 이번 시즌 RAW completeness를 `COMPLETE` 또는 `PARTIAL / BACKFILL REQUIRED`로 명시한다.
3. `raw_transcript/INDEX.md`에 시즌 범위와 PART 목록을 갱신한다.
4. 그 뒤 ROOM_ARCHIVE / LEDGER / CURRENT_STATE / FEEDBACK을 닫는다.

현재 컨텍스트에서 이미 사라진 원문은 만들어내지 않는다. 그 시즌은 PARTIAL로 정직하게 남긴다.
과거 전체 RAW 백필 완료를 다음 플레이 시작 조건으로 만들지는 않는다.

## 9. 업데이트 빈도

### Hot State
이동·합류·분리·통화·위기처럼 연속성이 민감할 때 필요하면 즉시 갱신한다.

### Rolling RAW
- 약 6~10개 왕복 또는 큰 장면 종료
- 큰 시간점프 / 큰 관계·자산 변화
- 방 이동 / 시즌 종료 직전

### Long State 즉시 체크포인트
- 사망/합류/이탈
- 큰 자산 상실 또는 취득
- 큰 이주
- 세계 국면 변화
- 큰 시간점프
- 플레이 종료/방 이동

### 일반 플레이
대략 3~6개의 중요한 결정 또는 하나의 큰 장면 묶음 후 한 번이면 충분하다.

## 10. 부담 제한

GM은 매 턴 세계 전체를 다시 시뮬레이션하지 않는다.
- 현재 장면에서는 Hot State 7항목 우선
- Long State는 충돌/필요가 있을 때 조회
- 최대 3개의 active world front
- 최대 5개의 unresolved major thread
- 활성 비도현 관계 edge는 보통 3~5개 이하
- 중요하지 않은 재고/주민/도로는 필요할 때만 고해상도화
- Rolling RAW는 보관용이며 정상 장면 생성 입력으로 다시 읽지 않는다.

## 11. 종료/방 이동

플레이어가 큰 장 종료 또는 방 이동 의사를 밝히면 별도 요청 없이 다음 순서로 정리한다.

1. **RAW Final Flush** — 접근 가능한 USER/GM 공개 원문 전체를 마지막 PART까지 저장하고 completeness 표시
2. **ROOM/ARC ARCHIVE** — 사건·선택·결과의 압축 요약 생성/갱신
3. **LEDGER** — 영구 변화만 기록
4. **CURRENT_STATE** — 다음 시즌 부팅용 장기 체크포인트
5. **LIVE** — 활성 장면이면 갱신, 종료되면 `INACTIVE / ARC CLOSED`
6. **FEEDBACK** — 사용자 피드백과 GM 자체 회고를 분리·압축하고 장기 규칙은 `PLAYER_FEEDBACK.md`에 통합
7. **RAW INDEX** — COMPLETE/PARTIAL 상태와 PART 목록 최종 확인

이 종료 루틴은 사용자가 매번 요청하지 않아도 자동으로 수행한다.

새 `NEXT_ROOM_BOOT_*` 파일을 만들지 않는다. 다음 방은 항상 `START_ROOM.md`에서 시작한다.
