## 0. 목적

이 문서는 외부 적대적 감사 결과를 그대로 규칙화하지 않고, 각 지적을 `ACCEPT / MODIFY / REJECT / VERIFY`로 분류해 실제 수정 범위를 잠그기 위한 결정문이다.

원칙:
- 감사와 수정은 분리한다.
- 문제를 찾았다는 이유만으로 새 규칙 파일을 추가하지 않는다.
- 심각도보다 실제 고장 경로와 플레이 영향이 우선이다.
- RAW 원문이 없는 영역의 재미 판정은 사실 확정이 아니라 검증 대기 가설로 남긴다.
- 사망·배신·상실 같은 결과를 할당량으로 만들지 않는다.

## 2. ACCEPT — 그대로 수용

### A1. 활성 LIVE_SCENE_STATE가 부팅 경로에서 보장되지 않는다
Severity: P0 운영결함

수용 이유:
- `STATE_PROTOCOL.md`는 ACTIVE `LIVE_SCENE_STATE.md`를 Hot State 권위로 정의한다.
- 반면 `BOOT.md`, `START_ROOM.md`, `NEXT_ROOM_BOOT_2032_01.md`의 부팅 순서에는 LIVE가 일관되게 포함되지 않는다.
- 현재 LIVE는 2032년 3월 산업단지 사고와 롤백 경계를 보유하고 있어 누락 시 실제 장면 손실 가능성이 있다.

결정:
- 부팅 진입점은 1개로 통일한다.
- ACTIVE LIVE가 있으면 Long State보다 먼저 현재 장면 오버레이로 읽는 경로를 강제한다.
- `CURRENT_STATE`와 `LIVE`가 서로 다른 날짜를 갖는 것 자체는 오류로 보지 않는다. 전자는 Long State 체크포인트, 후자는 진행 중 Hot State이기 때문이다.

### A2. MACRO_SPINE_V1의 현재 앵커와 즉시지시가 심각하게 낡았다
Severity: P1

수용 이유:
- Current anchor가 2027년 겨울이다.
- 실제 활성 플레이는 2032년 3월이다.
- FIRST IMPLEMENTATION GUIDANCE도 두 번째 외곽집 매입 직후를 가리킨다.

결정:
- 재앵커 완료 전에는 현재 플레이 부팅에서 실행지시 소스로 사용하지 않는다.
- 다음 구조 정리 때 `2032 기준 재앵커` 또는 `시간 비의존 압력 구조로 대체` 중 하나를 선택한다.
- `오래된 지시는 읽되 소급 실행하지 마라` 같은 방어문을 추가하는 방식으로 해결하지 않는다.

### A3. 규칙 추가형 기획 부채가 과도하게 빠르게 증가했다
Severity: P1

수용 이유:
- 같은 문제를 여러 파일에서 반복 규정한다.
- 부팅 필독 문서가 늘면서 서로 다른 우선순위·중복 규칙이 생겼다.
- 오류를 막기 위한 새 파일이 다시 새 부팅 복잡도를 만드는 루프가 확인됐다.

결정:
- 당분간 새 운영 규칙 파일 생성 금지.
- 새 피드백은 가능한 한 기존 상위 파일을 수정·압축한다.
- 다음 구조 정리 목표: 필수 부팅 문서 5~7개 이하.

### A4. 장기 연대기에서 인물 나이가 동결된 문제
Severity: P1

수용 이유:
- 2026~2027에 확정된 여러 인물 나이가 2032 CURRENT_STATE에서도 동일하다.
- 장기 단일 연대기의 핵심인 시간 변화가 캐릭터에 적용되지 않았다.

결정:
- `age`를 반복 수동 갱신하는 방식보다 출생연도/기준연도 기반으로 계산 가능한 구조를 우선한다.
- 나이 변화가 외모·직업·은퇴·건강·자녀 성장 등 실제 서사 변화로 이어질 수 있게 한다.

### A5. 루트 README/START 구조가 현재 주력 세계선과 불일치한다
Severity: P2

수용 이유:
- 루트 README는 여전히 구 4인 가족 세계선과 Thin Engine 개발을 현재 프로젝트처럼 설명한다.
- STRONGHOLD는 branch-local 자산으로만 존재해 저장소 첫 진입자가 현재 방향을 오인할 수 있다.

결정:
- STRONGHOLD 구조 정리 이후 루트 라우팅을 수정한다.
- Legacy / Canon v2 Family / STRONGHOLD를 명시적으로 분리한다.

## 4. REJECT — 감사자의 결론을 채택하지 않음

### R1. `CURRENT_STATE와 LIVE의 날짜가 다르므로 현재 시점이 두 개다`
기각 이유:
- Long State checkpoint와 Hot State active scene을 분리하는 구조 자체는 정상이다.
- 실제 결함은 LIVE가 부팅에서 보장되지 않는 것이다.

### R2. `10시간은 통과, 50시간은 이미 실패, 100시간은 구조적으로 불가`
기각 이유:
- 실제 플레이 시간 데이터가 없다.
- in-world 5.5년 진행량을 실제 플레이 시간으로 변환할 근거가 없다.
- 향후 내구성에 대한 적대적 가설로만 보존한다.

### R3. `좋은 게임이 아니라 좋은 아이디어 두 개뿐`
기각 이유:
- 감사자가 RAW 플레이를 읽지 못한 상태에서 게임 전체의 실제 재미를 확정할 수 없다.
- 보고서 자체도 재미 판정을 `검증 불가`라고 전제했다.

### R4. `Play First / Build Later는 존재하지 않는 전략`
부분 기각.

현재 제품화를 서두르지 않는 전략은 유지한다.
다만 Build 진입 조건이 없다는 비판은 수용한다.

향후 Build 검토 게이트 후보:
1. 연속성 부팅 구조가 안정
2. 플레이 RAW 자동보존 동작
3. 수차례 추가 플레이에서 선택/페이싱 품질 재검증
4. deterministic state와 AI GM 경계 초안 확정
5. 재미 핵심 루프가 최소 2~3개의 질적으로 다른 압력에서 반복 검증

위 게이트 전에는 대규모 웹 개발을 재개하지 않는다.

## 5. 지금 당장 유지할 핵심

다음은 외부 감사 때문에 약화시키지 않는다.

1. **협력자의 독립성** — 모든 인물이 박도현의 부하가 되지 않음.
2. **리셋 없는 단일 연대기** — 단 시간/노화가 실제로 작동해야 함.
3. **준비의 차등 효과** — 준비는 손실 확률·범위·회복속도를 실제로 바꿈.
4. **비우는 것도 강해지는 방식** — 축적만이 성장이라는 전제 거부.
5. **웹소설형 장면 + 자유행동** — AI GM이 필요한 핵심 영역.
6. **도현의 비영웅성/경계설정** — 단 항상 무비용 정답이 되지 않도록 함.

## 7. 금지할 대응

이번 감사 이후 다음 행동은 하지 않는다.

- `상실이 적다`는 이유로 캐릭터를 의도적으로 죽임
- `도현이 너무 합리적이다`는 이유로 성격을 강제로 무모하게 변경
- 문제 하나마다 새 규칙 파일 추가
- RAW 백필 완료 전까지 플레이 전체 중단
- AI를 제거하는 것을 제품 성공조건으로 설정
- 50시간/100시간 추정을 검증된 사실처럼 사용
- 오래된 MACRO_SPINE에 또 방어 규칙을 덧붙임

## 8. 최종 결론

STRONGHOLD는 폐기 대상이 아니다.
현재 가장 큰 병목은 핵심 재미 아이디어보다 **그 재미를 보존하려고 급속히 쌓인 GM 운영문서와 상태 라우팅 복잡도**다.

따라서 다음 작업의 목표는 `기능 추가`가 아니라:

> **한 개의 부팅 경로, 더 적은 권위 문서, 확실한 Hot/Long State 경계, 시간이 실제로 흐르는 캐릭터 상태, 신규 RAW 자동보존**

으로 정리하는 것이다.
