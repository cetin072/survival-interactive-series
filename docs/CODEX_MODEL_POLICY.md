# Codex Model Policy — Luna / Terra / Sol

상태: ACTIVE
적용 범위: `cetin072/survival-interactive-series`의 Codex 구현·수정·검수 작업

## 1. 목적
Codex 작업을 시작할 때마다 사용자가 모델을 고민하지 않도록 작업 성격에 따라 권장 모델과 추론 수준을 미리 지정한다.

모든 신규 구현 Issue / Codex 전달문에는 가능하면 첫머리에 다음을 포함한다.

```text
권장 모델: GPT-5.6 Terra
권장 추론: Medium
```

모델 선택은 비용 절약 자체보다 `필요한 품질을 가장 작은 모델로 안정적으로 달성`하는 것을 목표로 한다.

---

## 2. 기본 모델

### GPT-5.6 Terra — 기본값
대부분의 일반 구현은 Terra를 사용한다.

권장 작업:
- 일반적인 React / TypeScript 구현
- UI 컴포넌트 제작
- 단일 Issue 범위의 기능 추가
- 중간 수준 버그 수정
- 테스트 작성/수정
- 기존 구조를 따르는 리팩터링
- Netlify 설정의 일반 변경
- 명세가 충분히 정리된 작업

기본 추론:
- **Medium**

High로 올리는 경우:
- 여러 파일/계층에 걸친 변경
- 상태 동기화나 비동기 흐름이 복잡함
- 원인 불명의 버그 추적
- PR 리뷰 지적사항이 복합적임

프로젝트 기본 원칙:
> 모델이 별도로 지정되지 않은 일반 Codex Issue는 Terra + Medium으로 시작한다.

---

### GPT-5.6 Luna — 가벼운 반복작업
정답이 거의 정해져 있고 문맥 판단 부담이 작은 작업에 사용한다.

권장 작업:
- 문구/오타 수정
- README나 주석의 단순 변경
- 파일명/표기 정리
- 명확한 CSS 소폭 수정
- 기존 패턴을 그대로 복제하는 작은 컴포넌트
- 테스트 fixture / 더미 데이터 보정
- 반복적인 정리 작업
- 이미 해결책이 확정된 작은 PR 리뷰 수정

기본 추론:
- **Low 또는 Medium**
- 별도 지시가 없으면 Medium을 사용해도 됨

Luna를 쓰지 않는 경우:
- 아키텍처 판단
- 상태 모델 설계
- 보안/인증
- 여러 시스템 간 계약 변경
- 원인 불명의 복잡한 버그
- 대규모 리팩터링

---

### GPT-5.6 Sol — 복잡하거나 중요한 작업
실수 비용이 크거나 여러 설계축을 동시에 판단해야 하는 작업에 사용한다.

권장 작업:
- 아키텍처 설계/변경
- State Engine 핵심 구조
- Validator의 핵심 규칙 구조
- AI GM Contract / Structured Output 설계
- Hidden State와 Public State 경계
- Cloud Save 충돌/동기화 설계
- 보안·접근코드·비밀정보 취급
- 다수 모듈에 걸친 리팩터링
- 재현하기 어려운 복합 버그
- 큰 PR의 독립 최종 검수
- 기존 설계문서 사이의 충돌을 해석해야 하는 작업

기본 추론:
- **High**

아주 어려운 원인 분석이나 아키텍처 재설계:
- **xHigh** 검토 가능

Sol은 단순 UI/문구 작업에 기본 사용하지 않는다.

| M1 | Live State 기본 모델 | Sol | High |

이 표는 기본값이며 Issue 실제 범위가 달라지면 기획방에서 조정한다.

## 4. 모델 승급 규칙
작업을 시작한 모델이 막히면 무조건 같은 모델로 반복하지 않는다.

### Luna → Terra
다음 중 하나면 승급:
- 두 번 이상 같은 수정이 실패
- 예상보다 여러 파일을 건드려야 함
- 기존 코드 의미 해석이 필요함
- 테스트 실패 원인이 불명확함

### Terra → Sol
다음 중 하나면 승급:
- 설계 선택 자체가 필요함
- 상태/데이터 계약을 바꿔야 함
- 여러 하위시스템의 정합성을 동시에 판단해야 함
- 반복 수정 후에도 같은 오류가 재발
- 보안/권한/저장 일관성이 걸림
- 기획문서와 코드가 충돌함

승급은 실패가 아니라 작업 복잡도가 초기 예상보다 높았다는 뜻이다.

---

## 5. 모델 강등 규칙
Sol로 설계를 정리한 뒤 후속 반복 수정은 Terra 또는 Luna로 낮출 수 있다.

예:
1. Sol + High로 State Engine 구조 확정
2. Terra + Medium으로 구현 보완
3. Luna + Medium으로 문구/CSS/fixture 수정

항상 최고 모델을 쓰는 것보다 이 방식이 효율적이다.

---

## 6. Issue 작성 규칙
기획방에서 신규 GitHub Issue를 만들 때 다음 형식을 위쪽에 둔다.

```markdown
## Codex 권장 실행
- 권장 모델: GPT-5.6 Terra
- 권장 추론: Medium
- 승급 조건: 상태 구조 변경이 필요하면 Sol + High로 전환
```

사용자는 PC Codex에서 Issue를 시작하기 전에 이 값대로 모델/추론을 선택한다.

Issue에 별도 값이 있으면 본 문서의 일반표보다 **Issue 지정값이 우선**한다.

---

## 7. 원칙
- Luna는 `싼 모델`이 아니라 **명확하고 작은 작업용 모델**이다.
- Terra는 프로젝트의 **일상적인 기본 개발 모델**이다.
- Sol은 `항상 더 좋은 기본값`이 아니라 **복잡성과 실패 비용이 큰 작업용 모델**이다.
- 모델을 높이는 대신 Issue 범위를 작게 나누는 것을 우선 검토한다.
- 모델 선택 때문에 사용자가 구현 내용을 이해하거나 판단해야 하는 부담을 늘리지 않는다.

핵심:
> **작업마다 모델을 고르는 책임은 기획방이 가진다. 사용자는 표시된 모델과 추론 수준을 선택하고 실행하면 된다.**
