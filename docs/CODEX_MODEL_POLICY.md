# Codex Model Policy — Luna / Terra / Sol

상태: ACTIVE / SINGLE SOURCE OF TRUTH
적용 범위: `cetin072/survival-interactive-series`의 Codex 구현·수정·검수 작업

## 0. 단일 기준

Codex 모델 선택의 **유일한 공통 기준 문서**는 이 파일이다.

- 신규 Issue에는 이 정책에 따라 `권장 모델 / 권장 추론 / 승급 조건`을 적는다.
- Issue에 명시된 값은 해당 작업의 실행값이다.
- `engine/AGENTS.md`와 다른 운영문서는 모델 선택법을 복제하지 않고 이 문서를 참조한다.
- 과거 Issue나 과거 Milestone에 적힌 모델은 역사 기록일 뿐 현재 작업의 기본값이 아니다.

핵심:
> **작업의 중요도나 크기만 보고 Sol을 선택하지 않는다. 설계 불확실성과 판단 난이도로 선택한다.**

---

## 1. 10초 결정 규칙

작업 시작 전에 아래 순서로 판단한다.

### Q1. 정답과 수정 방법이 거의 정해져 있는가?
예 → **Luna + Medium**

예시:
- 문구/오타
- 작은 CSS
- fixture/더미데이터
- 이미 해결법이 확정된 단순 수정

### Q2. 설계는 이미 확정됐고 구현이 중심인가?
예 → **Terra + Medium**

예시:
- 일반 React/TypeScript 기능
- 명세가 분명한 단일 Issue
- 테스트 추가
- 기존 패턴을 따르는 리팩터링
- 일반 Netlify 설정/배포 수정

### Q3. 설계는 확정됐지만 여러 계층의 상태·검증·비동기 흐름을 함께 다뤄야 하는가?
예 → **Terra + High**

예시:
- 여러 파일/계층에 걸친 상태 구현
- Validator + UI + CI를 함께 연결
- 복잡한 상태 동기화
- 재현은 되지만 원인 추적이 까다로운 버그
- 큰 PR의 구현 보완/회귀검증

### Q4. 구현자가 설계 자체를 다시 결정해야 하는가?
예 → **Sol + High**

예시:
- 아키텍처 신규 설계/재설계
- State Contract 자체 변경
- Public/Hidden State 경계 재설계
- 저장 원본이 여러 개라 Source of Truth를 다시 정해야 함
- 보안/인증/권한 구조 설계
- 여러 설계문서가 충돌해 해석과 선택이 필요함
- 반복 수정에도 원인불명 상태 오류가 계속됨

### xHigh
기본값으로 사용하지 않는다.
다음처럼 기획방이 명시적으로 판단한 경우에만 검토한다.
- 대규모 아키텍처 재설계
- 매우 어려운 원인불명 시스템 오류
- 보안/데이터 손실 위험이 큰 복합 분석

## 2. 표준 4단계

| 등급 | 모델 / 추론 | 사용 기준 |
|---|---|---|
| A | **Luna + Medium** | 답이 거의 정해진 작은 반복작업 |
| B | **Terra + Medium** | 설계가 확정된 일반 구현 — 프로젝트 기본값 |
| C | **Terra + High** | 설계는 확정됐지만 상태·계층·회귀가 복잡한 구현 |
| D | **Sol + High** | 설계 판단 자체가 열려 있거나 구조적 충돌을 해결해야 함 |

기본값은 **B — Terra + Medium**이다.

중요:
- `큰 작업 = Sol`이 아니다.
- `중요한 작업 = Sol`도 아니다.
- 명세가 충분하면 큰 작업도 Terra + High가 맞을 수 있다.
- 반대로 코드 변경이 작아도 State Contract나 보안 경계를 새로 결정해야 하면 Sol이 맞을 수 있다.

## 3. 모델별 역할

### GPT-5.6 Luna
**명확하고 작은 실행 작업용.**

권장:
- 문구/오타
- README/주석 단순 수정
- 파일명/표기 정리
- 명확한 CSS 소폭 수정
- 기존 패턴 복제
- fixture/더미데이터 보정
- 해결책이 확정된 작은 리뷰 수정

피할 것:
- 상태 모델 설계
- 아키텍처 판단
- 보안/인증
- 원인불명 버그
- 여러 시스템 계약 변경

기본 추론: **Medium**

---

### GPT-5.6 Terra
**프로젝트의 기본 개발 모델.**

#### Terra + Medium
권장:
- 일반 React/TypeScript 구현
- 단일 Issue 기능 추가
- 테스트 작성/수정
- 기존 구조를 따르는 리팩터링
- 일반 Netlify 변경
- 명세가 충분히 정리된 작업

#### Terra + High
권장:
- 여러 계층/파일에 걸친 구현
- 상태 동기화
- Validator/Compiler/UI/CI 통합
- 복합 PR 리뷰 대응
- 원인 추적이 필요한 중상급 버그
- 실패 비용은 높지만 설계 자체는 이미 확정된 작업

핵심:
> **설계가 끝났다면 먼저 Terra를 생각한다. 복잡하면 High로 올린다.**

---

### GPT-5.6 Sol
**설계 판단과 구조적 문제 해결용.**

권장:
- 아키텍처 설계/변경
- State Engine 핵심 계약 설계
- Validator 규칙 체계 자체 설계
- AI GM Contract / Structured Output 계약 설계
- Hidden/Public State 경계 설계
- Cloud Save 충돌/동기화 구조 설계
- 보안/접근제어/비밀정보 구조
- 서로 충돌하는 설계문서 해석
- 재현하기 어려운 복합 시스템 오류
- 큰 구조 변경의 독립 최종 검수

기본 추론: **High**

Sol을 쓰지 않는 이유가 되는 것:
- 단순히 작업이 중요함
- 파일 수가 많음
- PR이 큼
- 사용자가 품질을 중요하게 생각함

이 요소만으로는 Sol 승급 근거가 아니다.

## 4. 승급 규칙

### Luna → Terra
다음 중 하나면 승급한다.
- 같은 수정이 두 번 이상 실패
- 예상보다 여러 파일 의미를 해석해야 함
- 테스트 실패 원인이 불명확
- 단순 반복작업 범위를 벗어남

### Terra Medium → Terra High
다음 중 하나면 먼저 **추론만 올린다.**
- 여러 계층을 동시에 수정
- 상태/비동기 흐름이 복잡
- 회귀 테스트 범위가 큼
- PR 리뷰 지적이 여러 시스템에 걸침
- 실패 원인 추적이 필요함

### Terra → Sol
다음 중 하나일 때만 모델을 승급한다.
- 설계 선택 자체가 다시 필요
- State/Data Contract를 바꿔야 함
- Source of Truth가 충돌
- Public/Hidden/보안 경계를 다시 정해야 함
- 기존 문서와 코드의 구조적 충돌
- Terra + High로도 반복적으로 같은 원인불명 오류가 남음

원칙:
> **Terra에서 막혔다고 곧바로 Sol이 아니라, 먼저 ‘추론 부족’인지 ‘설계 판단 필요’인지 구분한다.**

---

## 5. 강등 규칙

설계가 끝나면 모델을 낮춘다.

예:
1. Sol + High — State Contract 확정
2. Terra + High — 여러 계층 구현
3. Terra + Medium — 일반 보완
4. Luna + Medium — CSS/문구/fixture 마감

항상 최고 모델을 유지하지 않는다.

---

## 6. Issue 작성 규칙

모든 구현 Issue의 위쪽에는 가능하면 아래 4줄을 둔다.

```markdown
## Codex 권장 실행
- 권장 모델: GPT-5.6 Terra
- 권장 추론: Medium
- 선택 이유: 설계가 확정된 일반 구현
- 승급 조건: 상태계약 자체 변경이 필요하면 Sol + High
```

사용자는 모델을 직접 분석할 필요가 없다.
기획방이 Issue를 만들거나 수정할 때 이 정책으로 값을 정한다.

작업 중 조건이 바뀌면 Codex는 임의로 모델 선택을 반복 고민하지 않고:
- 현재 모델로 가능한 범위는 진행
- 승급 조건에 해당하면 `MODEL ESCALATION RECOMMENDED`로 보고
- 필요 시 기획방에서 다음 실행 모델을 다시 지정

## 7. 현재 프로젝트 예시

### GM Coprocessor v1 / Issue #22
- 설계: 이미 확정
- 구현: RUNTIME_STATE + Validator + GitHub Actions + Netlify State Console
- 계층: 여러 개
- 판단: 구현 복잡도는 높지만 새 아키텍처 발명이 중심은 아님

따라서:
- **Terra + High**
- 구현 중 State Contract 재설계가 필요할 때만 **Sol + High**

### 단순 State Console CSS 보정
- **Luna + Medium** 또는 Terra + Medium

### 향후 AI GM ↔ Engine 자동 연결 계약을 처음 설계
- 계약/아키텍처가 열려 있다면 **Sol + High**
- 계약이 확정된 뒤 구현은 **Terra + High/Medium**으로 강등

---

## 8. 최종 원칙

1. **기본은 Terra + Medium.**
2. **복잡한 구현은 Terra + High.**
3. **설계 자체가 열려 있을 때 Sol + High.**
4. **정답이 거의 정해진 작은 일은 Luna + Medium.**
5. 중요도·파일 수·PR 크기만으로 Sol을 쓰지 않는다.
6. 모델을 높이기 전에 Issue 범위를 더 명확히 할 수 있는지 먼저 본다.
7. 모델 선택 책임은 기획방이 가진다. 사용자는 Issue에 표시된 값을 선택하면 된다.

한 줄 요약:
> **Luna = 실행이 단순 / Terra = 구현 / Sol = 설계 판단. Terra 안에서는 복잡도에 따라 Medium ↔ High를 고른다.**
