## 왜 벤치마킹했나
원형: https://azuolas.mainline.inc/krepsys/
- 리투아니아 Ąžuolas의 72시간 가방 가이드는 8개 분류, 기본 항목 중심 준비율, 가족 수에 따라 바뀌는 입력 참고 수량, 간단한 항목별 목적 설명, 체크 시 기한 입력이 강점이다.
- 주력 가치는 **처음 준비할 항목을 쉽게 고르는 경험**이다. BAG-SIDE-01은 #515의 실제 수량·기한·꺼냄→부족→실제 보충·IndexedDB·JSON 백업을 보존해 **장기간 유지 관리**에서 차별화한다.
- 외부 페이지는 제품·정보 구조만 참고했다. 외부 코드·디자인 소스·설명문·이미지 자체를 복사하지 않았다. 원 사이트의 코드 라이선스를 확보하지 않았고 재사용 허가를 가정하지 않는다.

## 구현
1. 기존 개인 Alpha `/bag-lab/alpha.html` 3탭 유지. 첫 탭에 추천 기본 항목의 **개인 설정 목표 수량 충족** 미터와 추천 목록 바로가기를 보여준다. 100%는 안전 보장이 아니라고 표시한다.
2. '물품 관리' 탭 상단에 접을 수 있는 추천 목록. 8개 분류를 가로 칩으로 선택하며, 한 번에 한 분류만 렌더해 모바일 장문 스크롤을 줄인다. 총 49항목(기본/선택), 설명·예시 단위·목표량·실제 등록 여부를 보여준다. 목록은 `catalog.mjs`라는 독립 정적 모듈이다.
3. '등록하기' 클릭은 이름·분류·단위·목표만 **편집 폼에 미리 채움**. 실제 가방 묶음 수량은 0이고 명시적 저장 전까지 IndexedDB를 변경하지 않는다. 이미 같은 이름의 물품은 중복 생성 대신 그 물품 기록으로 이동한다.
4. 참고 인원 1~8명은 신규 폼의 사람별 예시 목표량만 곱한다. 공유품은 그대로 유지한다. 저장된 목표·실재고·가방 이름·백업 데이터는 바꾸지 않는다. 참고 인원은 **일시적인 UI 상태**이며 재방문 시 1명으로 시작한다. 가족 구성원별 별도 가방/공유 재고는 미구현.
5. 진행률 분모는 자체 선별 '기본' 추천 항목의 수다. 실제 가방에 있는 수량이 사용자가 설정한 목표 이상인 경우에만 증가한다. 주문 중은 제외한다. 등록만 했거나 실물 수량이 0이면 준비 충족으로 세지 않는다. 앱 기존 3개 상태 카드·수량·기한 정렬과 서로 독립이다.
6. 저장용 스키마 `schemaVersion:1`, `IndexedDB records/current/previous`, JSON 백업 `formatVersion:1`, 충돌/원자적 복구 구조 및 기존 샘플 시연 코드는 그대로다. **기존 사용자 기록을 업데이트·마이그레이션하지 않는다.**

## 반드시 알아둘 UI 한계
- '생수 1L', '간편식 3개' 등은 입력 폼의 **자리 표시용 예시 목표**이지 생존에 충분한 수량이 아니다. 첫 화면·목록·폼에서 이 사실을 설명하며 사용자가 목표 수량을 조정하게 한다. 가족 인원을 늘렸다고 별도 가족 물품이 자동 생성되는 것도 아니다.
- 기본/선택 분류는 편집 가능한 내부 초안으로, 국가기관이 인증한 등급이 아니다. 추후 실제 사용자 리뷰·국내 기준 검증에 따라 수정한다.
- 항목명으로만 기존 물품과 일치시킨다. 이름이 다른 유사 제품은 자동으로 합치지 않는다. 중복·혼동을 발견하면 사용자가 직접 수정한다.
- Android OS 알림·PWA 완전 오프라인·스토어 배포·광고/후원·서버 동기화는 이 변경에 없다.
- Preview·Production·다른 브라우저는 각기 독립 저장소. 다운로드한 백업은 암호화되지 않는다.
