## 콘텐츠 원칙

1. **전체 원고 신규 집필.** 기존 현실 생존지식(Automation C)은 복사하거나 약간 바꿔 붙이지 않는다. 필요하다면 해당 글을 `관련 생존지식` 링크로 제시한다. A-Wiki(허구 세계관)는 근거가 아니다.
2. **답부터 시작한다.** 제목의 '왜 필요한가?'에 첫 문장으로 직접 답한다. 이어서 일어날 법한 생활 상황 2~3문장으로 핵심 장점을 보여준다. 상황의 끝을 '하지만 이 물품이 모든 위험을 막지는 못합니다' 같은 상투적인 방어 문구로 닫지 않는다. 가공된 경험을 실화처럼 표현하지 않는다.
3. **고정 순서, 유연한 길이.** 모바일에서 헤딩 순서와 역할을 통일하지만, 설명할 것이 적은 품목을 억지로 늘리거나 중복 문구로 채우지 않는다. 한 문단 2~4문장, 짧은 소제목, 쉬운 한국어.
4. **선택과 사용은 구분.** 필요한 이유·사용법·구매 판단·수납·정기 점검을 섞지 않는다. 개별 제품명이나 광고 중심으로 쓰지 않는다.
5. **안전은 정확하게, 경고는 필요한 만큼만.** 공공기관·제조사 공식 지침 등을 출처로 기록하고, 효능·용량·보관기한·재난별 안전 행동을 근거 없이 단정하지 않는다. 독자의 실제 행동과 안전 판단을 바꾸는 경고만 관련 절에 한 번 설명한다. 당연한 한계·면책성 문구를 도입과 사용 설명에 반복하지 않는다. 물·의약품·정화·화학·전기·화기·침수처럼 위해가 큰 주제의 필수 안전정보는 생략하지 않고 공개 전 추가 검수한다.
6. **수량은 개인화.** 기존 카탈로그의 `exampleTarget`은 입력 예시이지 충분한 생존 수량이 아니다. 글에서 공식 필수량·완비 기준으로 바꿔 말하지 않는다.
7. **원본 보호.** 새 글 작성은 IndexedDB의 실제 수량·제품 기한·재고·백업/복원, 카탈로그 ID, A/B/C 자동화나 배포 설정을 수정하지 않는다.
8. **독자의 시간을 아낀다.** 문장마다 '다만', '보장하지 않습니다', '이 뜻은 아닙니다'를 붙이지 않는다. 해당 문장이 읽는 사람에게 새 정보·판단 기준·실천 방법을 주지 않는다면 삭제한다. 공식 출처는 근거를 제시하는 수단이지 매 문단을 변명하는 장치가 아니다.

## 계속 읽기 연결 규칙 — 2026-10-12 확정

**목표: 한 물품을 읽은 방문자가 다음 유용한 물품·현실 생존지식을 자연스럽게 발견하도록 한다.** 체류시간은 결과 지표이지, 클릭 수를 늘리려고 내용을 쪼개거나 허위 연결을 만드는 이유가 아니다.

- **본문 내부:** 관련 맥락이 생기면 검증된 현실 생존지식 1회 정도만 링크. 반복 링크로 본문 독서를 방해하지 않는다.
- **글 하단 고정:** (1) '이어서 읽기' — 관련 현실 생존지식(Automation C) 우선 1~2개, (2) '함께 챙길 물품' — 실제 게시된 생존가방 전용 글 1~2개, (3) '내 생존가방으로 돌아가기' — 앱의 물품 관리로 연결, (4) '근거 자료' — 기관/공식자료 링크를 분리하여 제공.
- **표시:** 내부 글은 제목과 1줄 설명을 가진 링크 또는 클릭 가능한 카드/버튼. 연관성과 실제 존재 여부를 검증한 링크만 노출하며, 아직 제작하지 않은 글은 버튼을 만들지 않는다.
- **사이트 내 이동:** 내부 연결은 같은 탭에서 읽기 흐름을 유지할 수 있게 하고 뒤로 가기를 방해하지 않는다. 앱 복귀에서는 작성 중인 물품·재고 상태를 훼손하거나 강제 저장하지 않는다.
- **외부 근거:** 공식 사이트의 원문/페이지로 직접 연결. 기관 이름과 자료명·근거 범위를 명시하고, 외부 사이트임을 구별한다. 출처는 구독/추천 글로 오인시키지 않는다.
- **유효성:** 게시 단계에서 모든 실제 URL을 확인한다. 게시되지 않은 링크와 404·빈 콘텐츠는 숨기거나 수정한다. 기존 본문에 있는 관련글도 업데이트 때 재확인한다.
- **분리:** 현실 생존지식(Automation C)과 창작물 기반 생존일기/세계관 위키(A-Wiki)는 구분한다. 창작물 장면을 별도 '이야기 속 사례'로 소개할 수는 있지만 실제 안전 근거로 제시하지 않는다.
- **점진적 확장:** 49편이 쌓이면 새 글을 단순 추가하는 대신 서로 관련된 문서의 '이어서 읽기' 링크도 보강. 안정적인 `catalogId`·URL은 유지.

## 데이터 연결: 최소 구조

- 기존 `guide-01`~`guide-49`를 **품목의 안정적인 참조키**로 사용. 품목명·분류·배열 순서로 글을 추측해 연결하지 않는다.
- 공개 시 글마다 별도의 고정 URL과 `catalogId`를 갖는다. 예: `guide-43` ↔ `/knowledge/bag/flashlight/` (경로는 연결 개발 시 확정; **현재 존재하는 페이지라고 주장하지 않음**).
- 물품별 소개 화면에는 "자세히 알아보기" 1개와 "내 가방"으로 돌아오는 경로를 제공한다. 기존 Automation C 문서는 본문으로 복제하지 않고 "더 읽기"로 연결.
- 처음에는 단순 정적 원고·명시적 ID 매핑을 우선하고, 관리 DB·자동 게시·새 스키마·별도 예약은 만들지 않는다.
- 기존 개인 물품은 사용자가 직접 이름을 정할 수 있다. `catalogId`에 대응하는 추천 항목만 1차 자동 연결하며 임의 이름의 물품까지 부정확하게 일치시키지 않는다.

## 품질 검수 및 업데이트

- 공개 전: 실제 `CATALOG` ID/품명 일치 → 신규 집필·중복 점검 → 출처 URL·내용 확인 → **첫 문장 즉답 / 과한 면책성 문구 제거** → 모바일 가독성 → 실질적 안전/개인정보 주의 → 사용자 승인.
- 생존일기 이야기 속 사례는 **소재 후보**이며 실제 재난 대응 근거로 직결하지 않는다. 현실 경험은 발생 상황·조건을 구분해 사실 확인한 뒤 원고를 개선한다.
- 개선 시: 기존 글 URL·catalogId 유지, `수정일 / 무엇이 바뀌었는지 / 근거`를 기록한다. 독자가 읽는 본문만 갱신하고 새 문서를 무분별하게 늘리지 않는다.
- **공통 템플릿/표현 승인 완료.** 이제 나머지 48편을 순차 신규 집필할 수 있다. 다만 개별 글의 내용·링크·고위험 안전정보는 발행 전에 별도로 검수한다. 앱 연결, PR 병합, Production 배포는 작업 범위별 QA/승인을 따른다.
