### 사용자는 이 정도만 말하면 된다

> 무엇을 실제로 점검했는지 / 실물과 앱 기록이 맞았는지 / 쓰면서 막힌 점 / 다음에 할 일이 분명해졌는지

자유롭게 한두 문장으로 알려도 된다. 별도 설문, 네 항목 전부 응답, 파일·사진·백업 제출을 요구하지 않는다. 답하지 않은 내용은 **미확인**이며 AI가 채우지 않는다. 일부 물품만 점검했거나 중단했다는 보고도 그대로 남긴다.

### AI 기록 절차

1. 이 로그의 같은 회차가 있는지 먼저 확인한다. 최초는 아래 SELF-001을 갱신하고, 다음의 별도 점검은 SELF-002처럼 같은 BAG-SIDE-01 아래 이어 쓴다. 같은 보고의 재전달은 새 회차/성과로 늘리지 않는다.
2. 원본은 기존 대화/비공개 운영 기록에 보존하고 원본 위치·보고일을 연결한다. 공개 GitHub에는 비식별 요약만 남긴다. 원문이 민감하면 인용하지 않고 ‘비공개 대화, 보고일’ 정도의 참조만 쓴다. 가족·연락처·주소·보관 위치·가방 전체 재고·상세 수량/기한·백업 JSON을 저장소/PR/공개 사이트에 옮기지 않는다. 공개 가능 여부가 애매하면 비공개 원본에 두고 요약에서 생략한다.
3. 아래 형식의 사실 부분은 사용자가 말한 범위만 요약한다. **사용자 자기보고 / AI 재현 QA / AI 가설**을 명시적으로 분리한다. 점검했다는 보고만으로 앱 저장·백업·장기 알림·반복 사용 성공을 추정하지 않는다.
4. 추가 보고는 같은 회차에 보고일과 변경 근거를 덧붙인다. 최초 계획과 원본 보고를 지우지 않고 정정 이력을 남긴다. 상충 보고는 ‘확인 필요’로 보존하고 임의로 최신/유리한 결과를 선택하지 않는다.
5. 실물 재고는 앱의 기존 물품 수정·꺼냄·실제로 넣음 기능으로 관리한다. 앱의 현재/직전 로컬 저장과 JSON 백업은 **재고 보존용**이며 이 실험 로그와 역할이 다르다. 이 로그가 앱을 자동 수정하거나 중앙에서 로컬 기록을 읽는 것은 아니다. 백업 다운로드 요청과 실제 파일 보관·복원 확인도 구분한다.
6. 중요한 막힘(기록 손실·반복 오류·다음 행동 불명확 등)만 관련 기존 Issue를 찾아 회차 링크와 재현 범위를 연결한다. 본문을 복제하지 않는다. 전략·범위 결정이 바뀔 때만 DECISION_LOG에 근거 회차를 연결하고, STRATEGY는 실제 증거가 방향을 바꿀 때만 수정한다. 운영 일지에 인계할 때도 요약·회차 링크만 사용한다. 기록 작업 COMPLETED/CI/PR 병합을 실사용 완료나 로드맵 VERIFIED·사람 검수 receipt로 바꾸지 않는다.

### 상태 판정 — 기존 실험 상태와 함께 사용

기존 RESEARCH/PLANNED/RUNNING/PASS/FAIL 등의 정의와 운영 DB 상태는 바꾸지 않는다. **실행 단계**와 **개선 필요 여부**를 나눠, 점검을 마쳤어도 문제가 남는 사실을 보존한다.

| 표시 | 필요한 근거 | 기존 실험 상태와의 관계 |
|---|---|---|
| 실행 예정 | 계획만 있고 실제 점검 보고 없음 | PLANNED. 결과 미수집 |
| 실제 실행 완료 | 사용자가 계획한 3종을 실제 점검했다고 명시 | 결과 미확인이면 RUNNING(결과 정리 대기). 일부만 실행했다면 RUNNING(부분 실행), 완료로 올리지 않음 |
| 결과 확인 | 보고된 일치 여부·어려움·다음 행동을 원본과 대조해 정리. 누락은 미확인으로 표시 | 자기보고 확인이며 독립 검증/사용자 최종 검수와 다름. 한 회차 종료는 가능하나 1인 자기보고만으로 실험 PASS/시장성/일반 고객 효과를 선언하지 않음 |
| 추가 개선 필요 | 보고에 실제 막힘·불일치가 있거나, AI 제안이면 가설로 별도 표기 | 위 실행 단계와 함께 표시. 후속 수정·재시험까지 완료했다는 뜻이 아님 |

1인 시험은 시장·전환율·장기 재사용 판정에 **INCONCLUSIVE(근거 제한)**다. 기술 테스트 PASS는 QA에만 표기한다. 미응답은 불만 없음/실패/0건으로 변환하지 않는다.
